# ChoreSync — Project Brief (portfolio hand-off)

> Factual summary of the project for use as raw material when writing portfolio copy.
> Built July 2026. Live on GitHub Pages, backed by Supabase.

---

## 1. The problem

A three-person shared house needed a fair way to divide recurring chores. Requirements
that emerged during scoping:

- Chores split so each person spends roughly **equal time**, not equal task count.
- A **weekly rotation** so nobody is stuck with the same job.
- **Bin duty** handled separately, since it's a short task that one or more people can volunteer for.
- **Reminders** on configurable days/times, delivered to phones.
- **Accountability** when someone doesn't finish.
- Must be **free**, and work across a **mixed iPhone/Android** household.

## 2. Product decisions (and what was rejected)

| Option considered | Outcome |
|---|---|
| Native iOS/Android app (React Native / Expo) | Rejected — iOS distribution requires a $99/yr Apple Developer account |
| Expo Go | Rejected — app lives inside another app, no home-screen identity |
| Telegram bot / email reminders | Rejected — user wanted notifications from the app itself, no third-party service |
| **Installable PWA + Supabase** | **Chosen** — free, own home-screen icon on both platforms, self-contained backend |

The deciding constraint was cost combined with the mixed-platform household. A PWA was
the only route to a real installable app with push notifications at zero cost.

## 3. The chore model

Chores were enumerated per zone, individually time-estimated, then balanced.

**v1 (mixed bundles, ~31 min each):** bundles deliberately mixed rooms to balance time —
A: hoover + kitchen surfaces (30), B: living room + corridor + kitchen scrub (31),
C: floors & wet (32).

**v2 (zone-based, ~37 min each):** when bath/shower tub, wall tiles and toilet were added,
the washroom became large enough to stand alone. This allowed a cleaner restructure into
one zone per person — A: hoover & living areas (37), B: upstairs washroom (37),
C: kitchen (38). A **one-minute spread**, and far easier to remember than mixed bundles.

Rotation: person *i* is assigned bundle `(i + weekIndex) mod 3`, so over any three weeks
each person does each zone exactly once.

## 4. Architecture

**Frontend** — vanilla JavaScript PWA (no framework), single-page with three tabs.
Service worker for offline app-shell caching and push handling. Web app manifest for
home-screen install.

**Backend** — Supabase:
- **Postgres** with Row Level Security; tables for household settings, per-week state, push subscriptions, and a reminder de-dupe log.
- **Realtime** (`supabase_realtime` publication) for live multi-device sync.
- **Edge Function** (Deno) that composes and sends notifications.
- **pg_cron + pg_net** to invoke that function every 5 minutes.

**Push** — Web Push with VAPID keys; private key held as an Edge Function secret,
public key shipped to the client.

**Hosting** — GitHub Pages serving a `/docs` folder (free HTTPS, required for service
workers and push). Deploys via `git push`.

## 5. Features built

- Deterministic weekly rotation — derived from the date, so no schedule is ever stored or maintained.
- Live sync across phones (tick a chore, others update instantly).
- **Gamification:** XP (1 minute of cleaning = 1 XP), levels every 100 XP, completion streaks, medal leaderboard, per-person progress rings, confetti on finishing a bundle.
- **Bins:** voluntary claim — any number of people can tap to volunteer for take-out and bring-in.
- **Scheduled notifications:** chore day, bins out, bins in, and an overdue nudge — each with configurable day and time, evaluated in the household's own timezone.
- **Carry-over system:** unfinished chores follow the *person* into the next week at half XP, with a configurable catch-up deadline.
- **Accountability:** live "at risk" flags, plus a rolling 8-week missed-week tally with a drill-down showing which weeks and which specific chores.
- Shared PIN gate, read-only past/future weeks, offline support.

## 6. Notable engineering problems solved

**Key namespacing to prevent data collisions.** Carried-over chores are stored in the same
per-week record as current chores. Because a carried chore can share an ID with the current
bundle-holder's identical chore, carry-over ticks are namespaced under a `co:` prefix —
otherwise one person ticking their chore would silently mark someone else's overdue item complete.

**Name-based matching across a schema change.** Restructuring the bundles moved **10 of 13
chores** into different bundles. Attributing carry-over by bundle position would have pointed at
the wrong person; matching by chore *name* keeps attribution correct across the restructure.

**Effective-dated configuration.** Rather than mutating the bundle definitions in place — which
would have retroactively rewritten history and corrupted XP and streaks — bundles are
effective-dated (`SWITCH_FROM`). Past weeks are always interpreted with the definitions that were
live at the time, and the change was scheduled to take effect at a week boundary so nobody's
in-progress week was disrupted.

**Derived state over stored state.** Carry-over, at-risk status and missed weeks are all computed
from existing tick data rather than stored in new tables. No migration was needed, and the system
self-corrects if someone ticks something late.

**Idempotency in a scheduled job.** A cron job firing every 5 minutes must not send duplicate
notifications. Reminders de-duplicate on `(household, date, kind, time-slot)`. Including the
*time slot* was a deliberate fix: keying on date alone meant changing a reminder to later the same
day was silently swallowed.

**A real bug, found and fixed.** The de-dupe row was originally written *before* the push was sent,
so any send failure marked the reminder as delivered and blocked all retries for the rest of the
day — failing silently. Changed to record only after a confirmed successful send.

**Debugging a distributed notification pipeline.** A missing notification could have failed at any
of six hops: pg_cron → pg_net → Edge Function → web-push → FCM → service worker. Isolated it by
querying `cron.job_run_details`, `net._http_response` and the de-dupe log, which proved the push was
accepted by the push service (`{"sent":1}`) and narrowed the fault to device-side delivery
(Android battery optimisation delaying wake-up).

**Security incident handled.** GitHub push protection blocked a commit containing a Postgres
`service_role` key that had been pasted into a SQL file. Resolved by restoring the placeholder and
amending the commit before it ever reached the remote, then auditing the repo for other secrets.
Public-safe values (publishable key, VAPID public key) are shipped deliberately; private keys live
only in Supabase secrets.

**Deployment debugging.** GitHub Pages was serving the repository README from the root instead of
the app, because the publishing source was set to `/` rather than `/docs`. Also required service
worker cache versioning to force installed clients to pick up new builds.

## 7. Verification approach

Rather than testing by hand in the browser, the pure logic was tested in isolation:

- Rotation fairness — confirmed each person does each bundle exactly once per 3-week cycle.
- Week-index maths — verified across month and **DST boundaries**.
- Simulated multi-week seasons to check XP totals, streak counting and missed-week logic against hand calculations.
- Carry-over verified specifically **across the bundle-restructure boundary**, including correct re-attribution and absence of key collisions.
- Leaderboard flag states enumerated to catch a case where a user showed "3 overdue" and "clean record" simultaneously.

## 8. Skills demonstrated

Requirements gathering and iterative product design · time-based fairness modelling ·
full-stack build (frontend, database schema, serverless, scheduled jobs) · PWA, service
workers and Web Push · Postgres with RLS, realtime publications and pg_cron ·
secure key handling · debugging distributed asynchronous systems · Git/GitHub workflow
and deployment.

## 9. Possible angles for the portfolio write-up

- *"Designing for fairness"* — the time-balancing problem and why equal task counts aren't equal effort.
- *"Free was the hardest constraint"* — how a cost ceiling and a mixed-platform household forced the PWA architecture.

- *"Six hops and a silent failure"* — debugging the notification pipeline.
- *"Gamification as behaviour design"* — XP, streaks and the carry-over/grace-week mechanic as an accountability system rather than a scoreboard.
